# 06 — Evaluation

> and [delivery backlog](18-delivery-backlog.md) supersede conflicting scope,
> rubric, schema, sample counts, commands and deployment assumptions below.
> Features here are proposals unless confirmed in the

The challenge's own words: no gold standard and no metric exist today — "nobody can say whether a pipeline is good enough to run unattended." Skony treats building that evidence as a primary deliverable, not an afterthought.

## Gold set

- **Size:** 30–50 documents (hackathon), extensible to 200+.
- **Stratification:** 3–5 bodies × ≥2 languages (DE+FR) × {born-digital, scanned} × affair types; includes deliberately hard cases (stamps, tables, annexes, handwritten elements).
- **Annotation:** field-level ground truth by a human, in the Skony schema, with source spans. Stored in `data/gold/` (inside the 100 MB submission budget).
- **Hygiene:** gold set is never in prompts; prompt tuning uses a separate dev slice to avoid overfitting the metric.

## Metrics

| Metric | Definition | Slices |
|---|---|---|
| Field precision / recall / F1 | verified-correct fields vs gold, per field | × language × body × doc kind |
| Auto-accept precision | correctness of fields the pipeline accepted without review | overall (headline trust number) |
| Abstention rate | share of fields abstained, by reason code | × doc kind |
| Provenance coverage | share of non-null fields with valid resolved spans | overall (target 100%) |
| Verification false-reject rate | correct values rejected by the guard (manual audit of rejects) | overall |
| Q/A pairing accuracy | correct question↔answer↔decision linkage | × body |
| Cost | tokens + CHF estimate per document | × model (8B/70B) |
| Latency | seconds per document, p50/p95 | × model |

**Headline reporting format** (README + technical report, generated by `make eval`):

```
| Field          | P     | R     | F1    | Abstain |
|----------------|-------|-------|-------|---------|
| affair_type    | 0.xx  | 0.xx  | 0.xx  | 0.0x    |
| submitters     | 0.xx  | 0.xx  | 0.xx  | 0.0x    |
| question_text  | 0.xx  | 0.xx  | 0.xx  | 0.1x    |
| answer_text    | 0.xx  | 0.xx  | 0.xx  | 0.2x    |
| decision       | 0.xx  | 0.xx  | 0.xx  | 0.0x    |
| — by language  | DE: F1 0.xx | FR: F1 0.xx |   |         |
```

## Baselines (SK-E4)

Same gold set, same scorer:
1. **Docling-only** — structure without affair semantics (expected: low field recall, shows the semantic gap).
2. **Ad-hoc prompting** — one generic prompt, no schema/vocab/verification (expected: shape drift, invented values — the failure mode the deck warns about).
3. **Skony** — must beat both on F1 *and* report provenance coverage the others cannot produce at all.

## Targets (pre-registered, not results)

These are commitments to measure against, set before the final runs — no number below is a measured result yet:

| Target | Value |
|---|---|
| Auto-accept precision | ≥ 0.95 |
| Provenance coverage | 100% of non-null fields |
| Seeded-hallucination catch rate | 100% |
| Field F1 (typed fields: type, dates, decision) | ≥ 0.90 |
| Field F1 (free text: question/answer spans) | ≥ 0.75 |
| Demo corpus cost (8B, self-hosted) | ≤ CHF 0.02/doc |

## Methodology commitments (what makes this rigorous)

- **Fixed scorer**: one deterministic scoring script; humans never "eyeball" metric outcomes.
- **Version pinning**: every published number carries `model_name`, `prompt_version`, `schema_version`, gold-set commit hash.
- **Honest slicing**: per-language and per-body numbers are shown even when they hurt; aggregate alone is considered misleading.
- **Error analysis**: top 10 failure examples documented in the technical report with root causes (OCR, layout anomaly, vocabulary gap…).
- **Insight framing**: results answer the challenge question — which schema parts generalise across parliaments and where fundamental differences remain. A well-evidenced *partial* answer is a success per the brief.

## Reproducibility

```bash
make eval        # rebuild gold metrics from committed artefacts
make eval-fresh  # re-run extraction on gold docs, then score (needs LLM access)
```

The eval report lands in `docs/eval/` and is inlined into `technical_report.md` at submission time.
